# Phase 3 — Confirm

A gate. Do not estimate anything until the user has answered.

Ask about the things that change the number. Do not ask about things you can decide
yourself, and do not present a menu where one option is obviously right — recommend it and
say why.

## What to confirm

**1. Scope and structure.** The module breakdown from Phase 2, or the client's structure
in FILL mode. Anything you propose to leave out.

**2. Which effort columns.** Typically UI/UX, back-end, front-end, mobile, AI. Two
questions matter:

- Is UI/UX priced, or absorbed into the front-end and mobile tasks?
- Is the non-functional module priced, or absorbed into each task?

Either can be a deliberate zero. If so, the rows stay and the cover explains why, because a
section priced at zero reads as considered while an absent section reads as forgotten.

**3. Mobile approach.** Cross-platform or native. This is usually the largest single lever
in the whole estimate: native is 1.2-1.5× the web front-end per feature and doubles across
two platforms, where a cross-platform framework lands close to 1×. If the documents leave
the choice open, recommend cross-platform and say what it saves.

**4. What the hours cover.** Development, developer unit testing and code-review fixes is
the default. Confirm whether a dedicated QA function, project management, business analysis
and any discovery phase are inside the number or quoted separately. If separate, the cover
will state the uplift the reader should apply.

**5. The competitive factor.** Default ×1.0 and say why: on a fixed-price bid with
unsettled requirements, a discount buried in engineering hours cannot be undone and hides
how much room there is. If the user wants a discount, apply it as a visible factor.

**6. Whether a cloud cost estimate is wanted too.** If infrastructure is in scope, the
skill can produce a second workbook pricing the environments. It needs the target cloud and
region, and a region is not optional: prices vary by region and a residency requirement may
have already decided it.

## How to ask

Group the questions. Give a recommendation for each. Say what each choice does to the
number where you can, in hours or in percent.

If the user has already answered something in their brief, do not ask it again; state what
you took from it.

## After the answer

Restate the confirmed decisions in a short block, then go to Phase 4. If an answer changes
the structure from Phase 2, redo the affected part of the analysis before estimating; do
not carry a stale breakdown forward.
