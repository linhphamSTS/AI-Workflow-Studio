### A file-level substring test is not a per-item check (external_image_ref) — 2026-07-28
- **Symptom:** the AEGI v2 proposal reported `external_image_ref`, "External image reference in word/_rels/document.xml.rels". v1 of the same proposal had not. Nothing about the images had changed.
- **Root cause:** the check asked whether the .rels file contained `TargetMode="External"` ANYWHERE **and** the word "image" ANYWHERE. Both are true of any document that has an embedded image and one ordinary hyperlink, because embedded images are themselves `.../relationships/image` entries. v2 differed from v1 only in that its case-study hyperlink was populated, and that single legitimate link tripped the alarm. Two unrelated conditions matching at file level say nothing about any one relationship.
- **Fix:** parse each `<Relationship>` element and flag only those whose `Type` ends in `/image` AND carry `TargetMode="External"`, reporting the offending target. Calibrated both ways before committing: the real document (hyperlink only) now passes, and a synthetic document with a genuine externally-linked image is still caught.
- **Generalisable rule:** when a check reads a whole file and ANDs two substring tests, it is testing the file, not the item. Parse the items and test each one. A checker that cries wolf on a legitimate hyperlink is worse than no checker, because the next real finding gets waved through with it. Calibrate every new or changed check in both directions, a true positive and a true negative, before trusting it.

### Em-dashes and Latin abbreviations are AI tells: banned outright, with no carve-outs — 2026-07-28
- **What the client said:** "content ko dùng ' — ' or eg vì nó dễ nhận biết là do AI làm ra". A spaced em-dash and `e.g.` are two of the fastest ways a reader decides a bid was machine-written, which costs credibility before a single technical point lands.
- **Why the previous rule was not enough.** `04_generate.md` already banned em-dashes, but only in five named prose fields, and it explicitly ALLOWED them in `problems_and_solutions` and `explanation_bullets` because there they act as a structural separator after a bold label. `format_reviewer.check_em_dash_in_prose` matched that scope: it skipped any paragraph starting with a bullet glyph, and skipped figure captions entirely. So the rule was satisfied while the delivered document still showed em-dashes in the two places a reader looks hardest: the bullets under every figure, and every caption. **A reader does not care whether a dash is structural.**
- **Fix, enforced at four layers so a slip cannot ship:**
  1. `04_generate.md`: the ban now covers all delivered content with the carve-outs explicitly withdrawn, plus a new ban on `e.g.` / `i.e.` / `etc.` / `viz.` / `cf.` with the English to use instead. Every content EXAMPLE in the prompt was rewritten to the colon form, because a builder copies the example, not the rule.
  2. `build_docx.py`: `_label_dash_to_colon()` rewrites `**Label** — body` to `**Label**: body` for every bullet (it already did this for Problems & Solutions only). Deliberately limited to the structural separator, which has one right answer; a mid-sentence dash needs a judgement call between a comma, a semicolon and two sentences, so that is left to the writer and caught by the reviewer.
  3. `format_reviewer.py`: `check_em_dash_in_prose` now scans every content paragraph including bullets and captions (shared `_iter_content_paragraphs`), and a new `check_latin_abbreviation_in_content` flags the Latin abbreviations. Word-boundary anchored so `Inc.`, `AED.` and version strings do not false-positive.
  4. `diagram_check.py`: the caption convention flipped from `<Type> — <Scope>` to `<Type>: <Scope>`, with a `caption_em_dash` warning replacing the old check that actively REQUIRED a dash.
- **Checked before tightening:** the template's verbatim Section 3 has 0 em-dashes and 0 Latin abbreviations, so widening the checks cannot produce a blocker on content we do not author. Do this check before tightening any content rule.
- **Generalisable rule:** when a style rule has a carve-out "because it is structural there", assume the carve-out will swallow the rule. Either the mark is acceptable to the reader or it is not. And a rule is only real once (a) every EXAMPLE in the prompt obeys it, and (b) an automated check enforces it. Prose guidance alone gets violated; that is now the second time on this exact rule.

### Versioned re-run froze the renderer — a lesson that made the skill stop improving — 2026-07-28
- **Symptom:** the diagram render/export layer was ported into this skill (`build_cloud` / `build_graph` / `build_sequence` became the PRIMARY renderers in `04_generate.md`), but a web-app **regenerate** of an existing workspace produced v2 PNGs that were **byte-identical to v1** — the new engine never ran.
- **Root cause — a self-learned lesson turned into a trap.** The Azure company-profile entry (2026-07-13) concluded that a versioned re-run should "reproduce the prior version's artifacts (**build script**, specs, `replacements.json`, `diagrams.json`, `manifest.json`)". Phase 0 reads this diary, so every regenerate dutifully copied v1's build script forward. v1 predated the port and used mingrammer, so the regenerate replayed mingrammer and silently opted out of the new renderers, the DPI fixes and the SA-grade structure. **The skill kept learning and the output stopped changing.**
- **Why the original lesson looked right:** reproducing artifacts *does* make a re-run stable and reliable — for CONTENT. The error was lumping the **build script** in with the content. Content stability is desirable; renderer stability is the opposite of improvement.
- **Fix — PROMOTED to `04_generate.md` ("VERSIONED RE-RUN — reuse the CONTENT, never the RENDERER"):** an explicit two-column table splitting what to reuse (plan, `replacements.json`, captions / intros / explanation bullets, slugs, target headings) from what to re-derive every time (renderer choice, `spec.json`, PNG/SVG/`.drawio`, the `.docx` assembly), plus the reason: *a run that replays the old build script opts out of every subsequent improvement*. If a re-render genuinely regresses, report it in Phase 6 instead of silently reinstating the old images.
- **Also enforced from the caller:** the web app now passes an explicit prior-version block into the generate prompt naming the previous version directory and repeating the reuse/re-derive split, so the instruction does not depend on the diary being read carefully.
- **Generalisable rule (the important one):** **a lesson that says "reuse what worked last time" must name exactly WHICH artifacts.** If it is allowed to cover the build/render layer, the skill freezes at the capability it had the day that lesson was written, and every later improvement is invisible. When writing a reuse lesson, always split *content* (safe to reuse — stability) from *capability* (never reuse — that is the thing being improved).


### Full-page cover image (inline) overflowed to a blank page 2 on SharePoint — 2026-07-13
- **Symptom:** the page-1 cover image (and a second full-page image later in the doc) looked fine locally, but uploaded to SharePoint Online (which reflows + auto-updates fields) it pushed a blank EXTRA page after it. Manually changing the image's text-wrap made the blank page disappear.
- **Root cause:** the two full-page images (8.27×11.69in ≈ the whole A4 page) were **INLINE**, sitting in zero-margin sections whose content area is exactly the full page. An inline image at 100% of the content height + the paragraph's own line-height/paragraph-mark exceeds the page by a hair → forces a new page → a blank page. SharePoint's reflow makes it worse (user: "bị kéo to ra").
- **Fix:** converted both full-page inline images to **FLOATING anchors** — `wp:inline` → `wp:anchor` with `behindDoc="1"`, `positionH/V relativeFrom="page"` offset 0,0, `wrapNone`, same extent. A floating image doesn't consume line height in the text flow, so the cover fills the page with no overflow (exactly the manual "change wrap" fix, baked into the template). Verified: 2 images now anchor (8.27×11.69, behindDoc=1, wrapNone), drawings 9 unchanged, XML well-formed, doc opens, 20 placeholders + TOC field intact, the image-heading TOC guard still passes.
- **Reusable rule:** a full-page / full-bleed image (≈ page size) must be a FLOATING anchor (behind text, page-relative 0,0, `wrapNone`) — NEVER inline. An inline image at ~full content height always overflows into a blank page, especially after SharePoint reflow. Content figures smaller than the text area may stay inline.

### Template images in Heading paragraphs leaked into the TOC on SharePoint — 2026-07-13
- **Symptom:** after uploading a generated proposal to SharePoint and letting it update the Table of Contents (template has `updateFields=YES`, so it auto-updates on open), some images were pulled into the mục lục / showed as stray TOC entries. It affected ONLY images ALREADY IN THE TEMPLATE — skill-generated diagrams (inserted into Normal paragraphs) were fine.
- **Root cause:** 3 image-only paragraphs in `templates/proposal_template.docx` carried a Heading style (2× "heading 2" styleId=3, 1× full-page image "heading 1" styleId=2). The template's TOC field is `TOC \h \u \z \t "Heading 1,1,Heading 2,2,…,Heading 6,6,"` — the `\t` switch collects **by STYLE NAME**, so ANY Heading-styled paragraph (even an empty image one) becomes a TOC entry. Note: an outline-level override (`w:outlineLvl w:val="9"`) does NOT help here because `\t` matches the style name, not the outline level.
- **Fix:** changed those 3 image paragraphs' `w:pStyle` from heading (id 2/3) → Normal (id 1) via python-docx, KEEPING their direct `jc`(center)/`spacing`/`ind` so the images don't move. Verified: image-paras-in-TOC 3→0, real headings-with-text unchanged (31), placeholders 20, TOC field intact, doc opens clean, size unchanged (3,066,380 B). Template stores styles by NUMERIC id (id 1=Normal, 2=heading 1, 3=heading 2) — resolve ids, don't match on the literal name.
- **Reusable rule:** an IMAGE must NEVER sit in a paragraph with a built-in `Heading *` style — a `\t "Heading…"` TOC collects it by style name. Keep figure/decorative images in Normal (or any non-`Heading *` style) with direct centering/spacing. When editing or regenerating the template, scan for a `w:drawing` inside a paragraph whose `w:pStyle` resolves to a Heading style and demote it to Normal.
- **PROMOTED to `build_docx.py`:** added `validate_template_image_headings(template)`, called at the top of `build()` right after `validate_template_placeholders`. It scans `word/document.xml` and HARD-FAILS (SystemExit) if any image paragraph uses a Heading style or an outline level — so this class of bug can't silently ship again if the template is ever rebuilt from an output. Verified both ways: PASSES the fixed template, FAILS the pre-fix template (git b13a210) catching all 3 offenders.
