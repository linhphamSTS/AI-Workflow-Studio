# Lessons Learned — /linhpham-technicalproposal

> **Self-learning store for this skill.** This file travels with the skill (git +
> profile junctions), so lessons recorded here apply to **every** run on **every**
> machine where the skill is deployed.
>
> - **Phase 0** reads this file at the start of every run and treats each entry as a
>   hard constraint / preference for the current proposal.
> - **Phase 6** appends a new entry at the end of every run AND **promotes** any
>   general lesson into the phase prompt / check that actually runs (mandatory — a
>   lesson left only here has not improved the skill).
>
> This file is a **diary** (it may grow freely — it never slows the skill). The skill's
> real memory is the **enforced rules** promoted out of here into the prompts/checks, so
> the log's size never matters. Goal: each proposal is more accurate, sharper, and freer
> of repeated mistakes than the last.

## How to read this (Phase 0)

Before doing anything else, internalise every entry below. If an entry names a
concrete fix (a format setting, a diagram rule, a content gap, a forbidden phrase),
apply it proactively this run — do not wait to rediscover the problem.

## How to write an entry (Phase 6)

Append to the **Entries** section, newest on top, using this shape:

```
### <Project> — <proposal type> — <YYYY-MM-DD>
- **Stack/architecture proposed:** … (+ why)
- **Format/layout issues hit & fix:** … (SharePoint compat, >=300 DPI, overflow, template structure, font/spacing drift, widow/orphan)
- **Diagram-quality issues & fix:** … (icon missing, chip/arrow collision, midline centring, label overflow)
- **Content gaps / client feedback:** … (what was missing or wrong, how corrected)
- **Do better next time (reusable):** … (checklist items future runs should apply up-front)
- **Generalisable rule?:** if a lesson is broadly true, also fold it into the relevant phase prompt (04_generate / 05b_format_review) — note here that you did.
```

Keep entries concrete and reusable. If a lesson is universal, promote it into the
phase prompts so it is enforced, and note the promotion here.

### A commitment with no scope is a promise over whatever the reader decides it covers — 2026-08-27

- **What this was:** a pass over the factual technical ASSERTIONS in a delivered bid, as opposed to its structure. The distinction that made it productive, and worth reusing: anything the document already declares as "to be measured later" is protected; anything asserted as fact is the exposure. Three findings generalised into the skill; the rest were project-specific and stayed in the project's own lessons.
- **★★★ THE FINDING: the client-facing proposal committed 99.9% availability "for the whole flow" while the bid team's own internal brief said, in as many words, not to sign an end-to-end SLA that includes the client's Oracle.** Two documents of one bid, one making the promise the other forbids. Nothing structural can see it: both sentences are well formed, in the right section, and the cross-document gate compared NUMBERS, never the scope a number is attached to. **Found by reading the client-facing commitment against the internal position prepared to defend it** — a pairing worth making deliberately, because the honest boundary usually already exists somewhere internal.
  - **The arithmetic refuses it before anyone argues.** Serial availability MULTIPLIES: five tiers at 99.9 and 99.95 per cent land near **99.64%, about 155 minutes a month**, and that is before the client-operated ERP at the end of the chain is counted at all.
  - **Promoted:** an **EVERY COMMITMENT MUST NAME ITS SCOPE** block in `04_generate.md` (availability is multiplicative, so name the chain; never commit end-to-end over a system the client operates; a durability claim must name the failure it survives), and `format_reviewer.check_commitment_scope`, which fails an availability percentage tied to a whole-chain phrase. Calibrated both ways on the real before and after files: catches the delivered wording, passes the corrected one.
- **★★ "RPO 0" backed by zone-redundant storage is RPO 0 for the loss of a ZONE, not of a region — and the word "region" appeared in NONE of that bid's six artefacts while RTO 4 hours was already committed.** Silence about a failure mode reads as a commitment to survive it. The rule promoted with the block above: name the failure a durability claim covers, and if regional recovery is out of scope, carry it as a Phase 2 item rather than leaving it unsaid.
- **★★ A requirement the client stated in terms went unanswered, and a keyword scan looked satisfied because it matched the wrong sentence.** They asked for the ceilings on record size, throughput and average processing time; the only sentence in the proposal containing the word "limit" was about a platform's message-size cap. **Answer a stated requirement with numbers and show the division** — "20,000 records in 15 minutes is 22.2 per second, about six concurrent sessions at 250 ms per call" is checkable, and being checkable is what makes the rest of the document credible. Promoted as the closing paragraph of the same block.
- **★★ A GUARD THAT MATCHES A PHRASE INSTEAD OF THE ARTEFACT SKIPS THE WORK AND REPORTS SUCCESS.** A post-assembly patch guarded on a Vietnamese phrase; a later, unrelated edit legitimately introduced that phrase, so the patch printed "already present, nothing to do" and did nothing. The failure mode is a cheerful success message, not an error. **Guard an idempotent patch on the artefact it builds** — the table, the section, the row — never on a word that happens to travel with it. Not promoted to code because it lives in per-project patch scripts, but it is the shape to check for in any of them.
- **★ When patching text into a document another tool generated, match its RUN STRUCTURE, not just its words.** `build_docx` renders `**label**: rest` with the colon in the NON-bold run. ### A file-level substring test is not a per-item check (external_image_ref) — 2026-07-28
- **Symptom:** the AEGI v2 proposal reported `external_image_ref`, "External image reference in word/_rels/document.xml.rels". v1 of the same proposal had not. Nothing about the images had changed.
- **Root cause:** the check asked whether the .rels file contained `TargetMode="External"` ANYWHERE **and** the word "image" ANYWHERE. Both are true of any document that has an embedded image and one ordinary hyperlink, because embedded images are themselves `.../relationships/image` entries. v2 differed from v1 only in that its case-study hyperlink was populated, and that single legitimate link tripped the alarm. Two unrelated conditions matching at file level say nothing about any one relationship.
- **Fix:** parse each `<Relationship>` element and flag only those whose `Type` ends in `/image` AND carry `TargetMode="External"`, reporting the offending target. Calibrated both ways before committing: the real document (hyperlink only) now passes, and a synthetic document with a genuine externally-linked image is still caught.
- **Generalisable rule:** when a check reads a whole file and ANDs two substring tests, it is testing the file, not the item. Parse the items and test each one. A checker that cries wolf on a legitimate hyperlink is worse than no checker, because the next real finding gets waved through with it. Calibrate every new or changed check in both directions, a true positive and a true negative, before trusting it.

### Em-dashes and Latin abbreviations are AI tells: banned outright, with no carve-outs — 2026-07-28
- **What the client said:** "content ko dùng ' — ' or eg vì nó dễ nhận biết là do AI làm ra". A spaced em-dash and `e.g.` are two of the fastest ways a reader decides a bid was machine-written, which costs credibility before a single technical point lands.
- **Why the previous rule was not enough.** `04_generate.md` already banned em-dashes, but only in five named prose fields, and it explicitly ALLOWED them in `problems_and_solutions` and `explanation_bullets` because there they act as a structural separator after a bold label. `format_reviewer.check_em_dash_in_prose` matched that scope: it skipped any paragraph starting with a bullet glyph, and skipped figure captions entirely. So the rule was satisfied while the delivered document still showed em-dashes in the two places a reader looks hardest: the bullets under every figure, and every caption. **A reader does not care whether a dash is structural.**
- **Fix, enforced at four layers so a slip cannot ship:**
  1. `04_generate.md`: the ban now covers all delivered content with the carve-outs explicitly withdrawn, plus a new ban on `e.g.` / `i.e.` / `etc.` / `viz.` / `cf.` with the English to use instead. Every content EXAMPLE in the prompt was rewritten to the colon form, because a builder copies the example, not the rule.
  2. `build_docx.py`: `_label_dash_to_colon()` rewrites `**Label** — body` to `**Label**: body` for every bullet (it already did this for Problems & Solutions only). Deliberately limited to the structural separator, which has one right answer; a mid-sentence dash needs a judgement call between a comma, a semicolon and two sentences, so that is left to the writer and caught by the reviewer.
  3. `format_reviewer.py`: `check_em_dash_in_prose` now scans every content paragraph including bullets and captions (shared `_iter_content_paragraphs`), and a new `check_latin_abbreviation_in_content` flags the Latin abbreviations. Word-boundary anchored so `Inc.`, `AED.` and version strings do not false-positive.
  4. `diagram_check.py`: the caption convention flipped from `<Type> — <Scope>` to `<Type>: <Scope>`, with a `caption_em_dash` warning replacing the old check that actively REQUIRED a dash.
- **Checked before tightening:** the template's verbatim Section 3 has 0 em-dashes and 0 Latin abbreviations, so widening the checks cannot produce a blocker on content we do not author. Do this check before tightening any content rule.
- **Generalisable rule:** when a style rule has a carve-out "because it is structural there", assume the carve-out will swallow the rule. Either the mark is acceptable to the reader or it is not. And a rule is only real once (a) every EXAMPLE in the prompt obeys it, and (b) an automated check enforces it. Prose guidance alone gets violated; that is now the second time on this exact rule.

### Versioned re-run froze the renderer — a lesson that made the skill stop improving — 2026-07-28
- **Symptom:** the diagram render/export layer was ported into this skill (`build_cloud` / `build_graph` / `build_sequence` became the PRIMARY renderers in `04_generate.md`), but a web-app **regenerate** of an existing workspace produced v2 PNGs that were **byte-identical to v1** — the new engine never ran.

### The stack and the architecture were never compared to each other

Three artefacts describe the same system and different steps produce them: `plan.tech_stack`
chooses the technologies, `plan.architecture` describes the shape, and the diagram specs draw
it. Nothing compared them, so they could disagree **while every artefact looked correct on its
own** — which is why a page-by-page review never found it.

`scripts/check_consistency.py` now gates that, run at the end of Phase 4 on the plan alone and
again in Phase 5b with the figures and the document. Six checks, calibrated against four
injected faults, all caught.

**Two clouds in one bid.** The stack chooses one provider and a figure is drawn from another's
template. It reached a delivered proposal: the body recommended one cloud sixty times, the
cached table of contents in the template still read another provider's name, and the cost
workbook priced the second one end to end. The gate now compares the provider vocabulary
across stack, architecture, figures and document, and separately checks that no figure is
built from a `<provider>_ref` template the stack did not choose.

**A figure promising a capability the stack cannot deliver.** A box reading `Kafka protocol
stream` and `Schema registry` beside a stack row naming a plain message queue commits to a
replayable log and to schema governance that nothing in the build provides. The figure is what
an evaluator believes, so the stack has to be able to honour it. Encoded as a table of
(promise vocabulary → the stack must name one of these), covering a replayable log, schema
governance, dead-letter handling, a search tier with analysers, a cache, a relational store
and an object store.

**The vocabulary is deliberately narrow.** Only names that identify a provider beyond doubt.
Generic nouns like compute, storage and functions are excluded, because a gate that reports a
contradiction on an ordinary word gets switched off and then catches nothing.

**One check stayed a warning on purpose:** a stack row naming a product the document never
mentions. A row can legitimately name an internal choice the prose describes in other words,
so failing on it would fire on sound proposals. The direction that costs a bid is the
contradiction, not the omission.
