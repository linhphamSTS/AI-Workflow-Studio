## How to read this (Phase 0)

Before doing anything else, internalise every entry below. If an entry names a
concrete fix (a format setting, a diagram rule, a content gap, a forbidden phrase),

```
### <Project> — <proposal type> — <YYYY-MM-DD>

```

Keep entries concrete and reusable. If a lesson is universal, promote it into the
phase prompts so it is enforced, and note the promotion here.

### Count the words the way the reviewer counts them, and look at the gutters after the lint passes — 2026-07-29
- **What this run was:** AEGI Group version 5, a fourth regenerate of the same bid, head-less, all thirteen optional sections ON. Result: 61 pages (v4 was 70), 7.43 MB, 10 figures, **0 diagram blockers, 0 format blockers, 24 checks passed, 0 leftover placeholders**, 52 diagram warnings against v4's 129.
- **The seam rule fired a second time, which is the real evidence it belongs in the prompt.** v4's own Phase 6 promoted "re-validate reused prose against the CURRENT ceilings". Between v4 (01:11) and this run, `format_reviewer.py` gained `check_narrative_length` and the optional ceilings were tightened (Security 320 to **260**, Delivery Roadmap 220 to **180**, Support Model 200 to **160**, per-entry 45 to **50**), and `04_generate.md` gained a whole WRITE TIGHT table. v4's prose, which shipped with 0 blockers, walked in with **14 breaches**: twelve total-capped sections over (Executive Summary 588 against 260, Summary 471 against 200, Mobile 234 against 160, Purpose 213 against 150, plus eight more), `problems_and_solutions` averaging 143 words against 55 per pair, and `references` at 76 in one paragraph. All fixed to 107 to 259 words with no entry dropped from any list. **The rule works only because a run measures BEFORE assembling** (see the next point); nothing in the pipeline would have caught the narrative ceilings until the format review, four minutes of rendering later.
- **THE lesson of this run: measure the way the reviewer measures, not the way the JSON reads.** Three mismatches, each of which silently passes an author's own check and fails the reviewer's. **Promoted to: `04_generate.md`** (a new block under the WRITE TIGHT ceiling table).
  1. `build_docx._stringify_value` renders each `problems_and_solutions` pair as **two** paragraphs (`● <problem>` and `**Solution:** <solution>`) and `check_narrative_length` measures the **longest paragraph**, so the reviewer's ceiling is per half while `04_generate.md` states 55 **per pair**. The two readings differ by 2x. Satisfying the strict one (pair total at most 55, neither half over 30) satisfies both, and ten pairs written that way still carried the quantified pain and the acceptance criterion.
  2. The rendered prefixes are counted as words by `str.split()`: `●` and `Solution:` each cost one, so author to about 50 against a 55 ceiling rather than measuring to the last word and losing on a glyph.
  3. **Nothing enforces the 30-word `explanation_bullets` ceiling.** Neither `format_reviewer.py` nor `diagram_check.py` measures it. All four diagram agents self-reported "max 30 words" while **seven** bullets were 31 or 32, each agent having counted with its own rule. The run's own merge gate caught them. Do the counting in the merge step with `len(s.split())` and refuse to write `diagrams.json` on a breach; never accept an agent's self-reported count as the measurement.
- **A ceiling checker in the generator is worth more than the same rule written down.** `specs/_ceiling_check.py` measures narrative totals, per-ENTRY worst case (rendering list values the way `_stringify_value` does), the required array SHAPE for `team_roles` and every `techstack_*`, and the forbidden tokens (em-dash, spaced en-dash, Latin abbreviations, `\n\n`). Run against v4's file it printed all 14 breaches in one pass, before a single render. Run against the new file it printed `ALL CEILINGS OK`, and the reviewer then agreed on every one. That is the difference between a rule and a gate.
- **`build_graph` width in TB is set by the SUM of edge-label widths in the busiest rank gap, not by card count.** Every labelled edge becomes a virtual label node in an intermediate rank. Shortening five labels on the context diagram (`OpenID Connect` to `OIDC` on three edges) took predicted width from 16.82in to 15.14in and on-page text from 4.68 pt to **5.24 pt**, against v4's 4.41 pt, with height down from 6.04in to 5.47in. The counter-intuitive half: **deleting three edges made it 2.5in WIDER** because `mincross` reordered the ranks. Card overhead is fixed at about 1.45in each, so about 5 cards per rank is the ceiling before gotcha 9 bites. **Promoted to: `04_generate.md` gotcha 13.**

- **The biggest lesson, and it sits exactly on the reuse/re-derive seam.** `04_generate.md` says reuse the explanation bullets as CONTENT and re-derive the render. Both halves are right, but the seam has a trap nobody had hit yet: **a bullet's bold label names a node in the PREVIOUS version's diagram.** Re-authoring every spec renamed or merged most nodes ("UAE PASS" became "National digital identity", nine shared contexts became eight, "Argo CD reconciliation" became "Declared state reconciled continuously"), so replaying v2's bullets verbatim would have shipped ~30 bullets describing boxes the reader cannot find. `diagram_check`'s `explanation_orphan` is a WARNING and only fires when *no* word of the bold label appears anywhere in the `.drawio`, so it catches almost none of this. Correct behaviour: reuse the SUBSTANCE of every bullet and re-point the bold label at a node that exists in the new render, one diagram at a time. Content reuse is not a byte copy.
- **`build_cloud` adjacent-column edge label budget is HALF the gutter, and the renderer will not tell you which label broke it.** `data_residency_security` rendered with `label_overlap`. Instrumenting `PIL.ImageDraw.text` found no text-on-text collision at all, because the collision was edge-label-versus-ICON: `'purpose checked on every read'` (338 px) started 10 px inside the source icon's right edge. Cause is `_edge` + `_longest_mid`: a same-row adjacent edge is routed `[sp -> (mx, y) -> (mx, y) -> ep]`, the two horizontal runs are equal length, and `_longest_mid` takes the FIRST one, so the label is centred a **quarter** of the way across the gap rather than half. Usable width is therefore `(COL_GAP + 2*COL_PAD + CELL_W - ICON) / 2`, about **318 px** at `S=3`, roughly 26 characters. Measuring all 6 cloud specs statically found 25 labels over the naive gutter width and confirmed only the ones over 318 px actually collide. Shortening 12 labels cleared it in one re-render instead of a guess-and-render loop.
- **A correction to an earlier lesson: `build_cloud` DOES route multi-column edges around the columns they span.** `_plan_edges` marks any edge spanning two or more columns as a `skip` and `_route_skip` sends it out through the source-side gutter, along a clear bus lane BELOW the boxes, and back up the target-side gutter, staggered per edge. So the older advice to avoid long edges was over-cautious: they are safe. The real cost is different, and it is a layout cost: every skip edge adds a bus lane, so the reuse map's four skips pushed it to 5.58in and left a visible dead band above the shared band. Budget skip edges for HEIGHT, not for collisions.
- **The case-study defect recurred exactly as predicted, and the repair shape improved.** The template still ships `...comparable to {{CASE_STUDY_TITLE}}.this link` with the URL inside a `HYPERLINK` field's `instrText`, and `build_docx.py` still flattens the field away, so v3 assembled as `...programme.this link` with no link at all. The post-assembly repair was re-derived rather than copied, and this time it binds a real `w:hyperlink` to a new external relationship in `word/_rels/document.xml.rels` instead of rebuilding a HYPERLINK field: a relationship-backed link renders as a link the moment the file opens, and a field is what the run-merge destroyed in the first place. It is not idempotent against a rebuild, so re-running Phase 5a silently reinstates `...programme.this link`. Same failure shape as the existing "do not re-run 5a for a spacing auto-fix" rule, different patch.

### A file-level substring test is not a per-item check (external_image_ref) — 2026-07-28
- **Symptom:** the AEGI v2 proposal reported `external_image_ref`, "External image reference in word/_rels/document.xml.rels". v1 of the same proposal had not. Nothing about the images had changed.
- **Root cause:** the check asked whether the .rels file contained `TargetMode="External"` ANYWHERE **and** the word "image" ANYWHERE. Both are true of any document that has an embedded image and one ordinary hyperlink, because embedded images are themselves `.../relationships/image` entries. v2 differed from v1 only in that its case-study hyperlink was populated, and that single legitimate link tripped the alarm. Two unrelated conditions matching at file level say nothing about any one relationship.
- **Fix:** parse each `<Relationship>` element and flag only those whose `Type` ends in `/image` AND carry `TargetMode="External"`, reporting the offending target. Calibrated both ways before committing: the real document (hyperlink only) now passes, and a synthetic document with a genuine externally-linked image is still caught.
- **Generalisable rule:** when a check reads a whole file and ANDs two substring tests, it is testing the file, not the item. Parse the items and test each one. A checker that cries wolf on a legitimate hyperlink is worse than no checker, because the next real finding gets waved through with it. Calibrate every new or changed check in both directions, a true positive and a true negative, before trusting it.

### Em-dashes and Latin abbreviations are AI tells: banned outright, with no carve-outs — 2026-07-28
- **What the client said:** "content ko dùng ' — ' or eg vì nó dễ nhận biết là do AI làm ra". A spaced em-dash and `e.g.` are two of the fastest ways a reader decides a bid was machine-written, which costs credibility before a single technical point lands.

### The stack and the architecture were never compared to each other

Three artefacts describe the same system and different steps produce them: `plan.tech_stack`
chooses the technologies, `plan.architecture` describes the shape, and the diagram specs draw
it. Nothing compared them, so they could disagree **while every artefact looked correct on its
own** — which is why a page-by-page review never found it.

`scripts/check_consistency.py` now gates that, run at the end of Phase 4 on the plan alone and
again in Phase 5b with the figures and the document. Six checks, calibrated against four
injected faults, all caught.

**Two clouds in one bid.** The stack chooses one provider and a figure is drawn from another's
template. It reached a delivered proposal: the body recommended one cloud sixty times, the
cached table of contents in the template still read another provider's name, and the cost
workbook priced the second one end to end. The gate now compares the provider vocabulary
across stack, architecture, figures and document, and separately checks that no figure is
built from a `<provider>_ref` template the stack did not choose.

**A figure promising a capability the stack cannot deliver.** A box reading `Kafka protocol
stream` and `Schema registry` beside a stack row naming a plain message queue commits to a
replayable log and to schema governance that nothing in the build provides. The figure is what
an evaluator believes, so the stack has to be able to honour it. Encoded as a table of
(promise vocabulary → the stack must name one of these), covering a replayable log, schema
governance, dead-letter handling, a search tier with analysers, a cache, a relational store
and an object store.

**The vocabulary is deliberately narrow.** Only names that identify a provider beyond doubt.
Generic nouns like compute, storage and functions are excluded, because a gate that reports a
contradiction on an ordinary word gets switched off and then catches nothing.

**One check stayed a warning on purpose:** a stack row naming a product the document never
mentions. A row can legitimately name an internal choice the prose describes in other words,
so failing on it would fire on sound proposals. The direction that costs a bid is the
contradiction, not the omission.
