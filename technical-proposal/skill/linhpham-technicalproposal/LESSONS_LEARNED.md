### Template images in Heading paragraphs leaked into the TOC on SharePoint — 2026-07-13
- **Symptom:** after uploading a generated proposal to SharePoint and letting it update the Table of Contents (template has `updateFields=YES`, so it auto-updates on open), some images were pulled into the mục lục / showed as stray TOC entries. It affected ONLY images ALREADY IN THE TEMPLATE — skill-generated diagrams (inserted into Normal paragraphs) were fine.
- **Root cause:** 3 image-only paragraphs in `templates/proposal_template.docx` carried a Heading style (2× "heading 2" styleId=3, 1× full-page image "heading 1" styleId=2). The template's TOC field is `TOC \h \u \z \t "Heading 1,1,Heading 2,2,…,Heading 6,6,"` — the `\t` switch collects **by STYLE NAME**, so ANY Heading-styled paragraph (even an empty image one) becomes a TOC entry. Note: an outline-level override (`w:outlineLvl w:val="9"`) does NOT help here because `\t` matches the style name, not the outline level.
- **Fix:** changed those 3 image paragraphs' `w:pStyle` from heading (id 2/3) → Normal (id 1) via python-docx, KEEPING their direct `jc`(center)/`spacing`/`ind` so the images don't move. Verified: image-paras-in-TOC 3→0, real headings-with-text unchanged (31), placeholders 20, TOC field intact, doc opens clean, size unchanged (3,066,380 B). Template stores styles by NUMERIC id (id 1=Normal, 2=heading 1, 3=heading 2) — resolve ids, don't match on the literal name.
- **Reusable rule:** an IMAGE must NEVER sit in a paragraph with a built-in `Heading *` style — a `\t "Heading…"` TOC collects it by style name. Keep figure/decorative images in Normal (or any non-`Heading *` style) with direct centering/spacing. When editing or regenerating the template, scan for a `w:drawing` inside a paragraph whose `w:pStyle` resolves to a Heading style and demote it to Normal.
- **PROMOTED to `build_docx.py`:** added `validate_template_image_headings(template)`, called at the top of `build()` right after `validate_template_placeholders`. It scans `word/document.xml` and HARD-FAILS (SystemExit) if any image paragraph uses a Heading style or an outline level — so this class of bug can't silently ship again if the template is ever rebuilt from an output. Verified both ways: PASSES the fixed template, FAILS the pre-fix template (git b13a210) catching all 3 offenders.

### Template-placeholder gap → empty section bug (caught on Kenneth) — 2026-06-28
- **Symptom:** delivered docx had a `Mobile App Strategy` HEADING with an empty body (heading sat directly above the next section). `replacements.json` had the full `mobile_app_strategy` text — data was fine, rendering was not.
- **Root cause:** `templates/proposal_template.docx` had the heading but its body paragraph was a literal EMPTY paragraph — the `{{MOBILE_APP_STRATEGY}}` placeholder was missing (every other content section had its `{{KEY}}` slot; this one was lost when the template was stripped from a prior output). No placeholder ⇒ the non-null value had nowhere to render; `drop_section_if_empty` correctly did NOT drop the heading (data was non-empty) ⇒ heading-with-empty-body. The format reviewer can't catch it (no `{{}}` left to flag).
- **Fixes (SKILL, so all future projects are safe):**
  - **Template:** added a Normal paragraph `{{MOBILE_APP_STRATEGY}}` under the heading. Cross-checked all content keys vs the template's `{{}}` set — mobile was the only gap (now 20 placeholders, all covered).
  - **Build guard:** new `validate_template_placeholders()` in `build_docx.py`, called at the top of `build()`. Scans the template's raw XML for `{{KEY}}` and FAILS the build (SystemExit, clear message) if any content key with a truthy value lacks a slot. Exempts structural keys (`diagram_captions`); skips `null` values. Verified: fixed template PASSes, pre-fix template FAILs naming `mobile_app_strategy`, `null` mobile PASSes (no false positive).
- **"Only real-mobile projects show this section" (user requirement):** already enforced — `04_generate.md` says set `mobile_app_strategy` to `null` when mobile is out of scope, and `drop_section_if_empty` removes the heading. Confirmed end-to-end: `null` → heading ABSENT, 0 leftover placeholder. So mobile-in-scope → rendered with content; no-mobile → section dropped entirely.
- **Reusable rule:** when stripping a template from a prior output, DIFF the resulting `{{}}` set against the Phase-4 content schema — any content key without a slot is a latent empty-section bug. The build guard now does this automatically; keep it. A content section needs EITHER a `{{KEY}}` slot (populated) OR an intentional `null` (dropped) — never a bare heading. The build-time guard (not the reviewer) is the right layer, because placeholders are gone by review time.
